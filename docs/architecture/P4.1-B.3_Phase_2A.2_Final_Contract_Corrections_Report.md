## 2. Comprehensive Resolution of the Six Review Items

### Item 1 (Critical): Case 4 & Case 8 Aligned with Verify-Before-Cancel Contract
- **The Issue in 2A.1:** Case 4 (Desired = `alarm`, both Alarm and Notif present) specified immediate cancellation of the stray notification upon refreshing the alarm, violating the core invariant: $\text{Schedule/Refresh} \longrightarrow \text{Verify} \longrightarrow \text{Cancel Old}$.
- **Corrected Contract:**
  1. Call `Alarm.set()` for desired deterministic alarm ID.
  2. Verify Level 1 (invocation completed returning `true`).
  3. Verify Level 2 (`Alarm.getAlarm(id)` exists with matching ID and timestamp).
  4. **ONLY AFTER successful Level 1+2 verification:** Cancel the obsolete stray Notification (`flutterLocalNotificationsPlugin.cancel(notifId)`).
  5. **IF verification fails:** **DO NOT cancel the old notification.** Both remain temporarily active, guaranteeing the user never loses alert coverage, and the day is marked **incomplete** for retry.
  6. Symmetrical logic applied to Case 8 (Desired = `notification`, both present).
- **Updated Document:** `Phase_2A.1_Scheduling_Decision_Matrix.md` (Table cases 4 & 8, Section 4.1).

### Item 2 (Critical): Complete Specification of `cancelAlarmSafely`
- **Method Signature:**
  ```dart
  Future<bool> cancelAlarmSafely(
    int id, {
    DateTime? expectedScheduledTime,
    String? expectedAssetAudioPath,
  });
  ```
- **Execution Pipeline & Answers to Inquiries:**
  1. **Source of `scheduledAt`:** Primary source is `expectedScheduledTime` passed by scheduler; verified against `alarm.dateTime` queried from `Alarm.getAlarm(id)`.
  2. **Ownership Proof:** ID alone is **insufficient**. Must fall within prayer range ($24,010,100 \le \text{id} \le 99,123,149$) AND `alarm.assetAudioPath` must match a confirmed prayer audio asset (`fajr_azan.mp3` or `adhan.mp3`). If asset mismatches, **aborts immediately** without stopping (returns `false`).
  3. **Behavior when `getAlarm(id)` is null:** Returns `true` (idempotent success; the target alarm is already nonexistent/stopped).
  4. **Active Ringing Check:** Calls `await Alarm.isRinging(id)`. If `true`, aborts cancellation (returns `false`), protecting the user's active Adhan.
  5. **Temporal Guard Window:** If $|\text{DateTime.now}() - \text{scheduledTime}| \le 15\text{ seconds}$, aborts cancellation (returns `false`).
  6. **Failure Handling:** If `Alarm.stop(id)` throws or fails, returns `false`, causing the scheduler to preserve state and flag the day incomplete.
- **Updated Document:** `Phase_2A.1_Notification_Ownership_and_Cancellation.md` (Section 3).

### Item 3 (Critical): Legacy FLN Notifications Across Reboot & Residual Behavior
- **Verified Android Manifest Declarations:**
  Direct inspection of `android/app/src/main/AndroidManifest.xml` proves:
  ```xml
  <uses-permission android:name="android.permission.RECEIVE_BOOT_COMPLETED" />
  <receiver android:exported="false"
      android:name="com.dexterous.flutterlocalnotifications.ScheduledNotificationReceiver" />
  <receiver android:exported="false"
      android:name="com.dexterous.flutterlocalnotifications.ScheduledNotificationBootReceiver">
      <intent-filter>
          <action android:name="android.intent.action.BOOT_COMPLETED" />
          <action android:name="android.intent.action.MY_PACKAGE_REPLACED" />
          <action android:name="android.intent.action.QUICKBOOT_POWERON" />
          <action android:name="com.htc.intent.action.QUICKBOOT_POWERON" />
      </intent-filter>
  </receiver>
  ```
- **FLN 21.0.0 Reboot Mechanics:**
  1. FLN persists scheduled requests in Android `SharedPreferences`.
  2. On reboot (`BOOT_COMPLETED`) or update (`MY_PACKAGE_REPLACED`), `ScheduledNotificationBootReceiver` wakes up.
  3. **Expired Notifications:** Any notification where `scheduledDate <= now` is **automatically discarded and purged from storage**. It is never re-armed.
  4. **Future Notifications:** Re-registered with Android `AlarmManager`.
- **Legacy Payload Tracing:**
  Traced from `schedule_weekly_prayers_usecase.dart` (lines 138–201):
  - Adhan: `adhan_simple_${prayer.key}`
  - Iqama: `iqama_${currentId}_${prayer.name}`
  - Azkar: `azkar_after_prayer`, `azkar_morning`, `azkar_evening`
- **Resolution & Residual Legacy Behavior Classification:**
  - Bulk `cancelAll()` is strictly forbidden (would destroy widgets and persistent alerts).
  - Targeted cleanup queries `pendingNotificationRequests()`, filters `id < 1000` matching these prefixes, and cancels them safely.
  - Because the legacy scheduler scheduled $\le 5$ days in advance, any legacy notification naturally expires within $\le 5$ days.
  - Formally classified as **`Residual Legacy Behavior`**: Fully mitigated via targeted payload cleanup with natural 5-day expiration horizon.
- **Updated Document:** `Phase_2A.1_Notification_Ownership_and_Cancellation.md` (Section 5).

### Item 5 (High): Legacy Cleanup Marker Ringing Exemption Policy
- **Tripartite State Classification:**
  1. **Successfully Stopped:** Future non-ringing alarm cancelled.
  2. **Intentionally Exempted (Active Ringing):** Alarm is actively ringing in user's ear.
     - **Safety Invariant:** This is **NOT a failure** of the cleanup routine; it is an intentional, safety-critical protection of active user audio.
     - The alarm has already triggered; it is in-flight audio that will self-terminate upon completion ($\le 3$ minutes) and will never re-arm.
  3. **Actual Failure:** Platform channel exception on a non-ringing alarm.
- **Marker Writing Policy:**
  - If all legacy alarms were stopped and NONE were ringing $\implies$ Write `legacy_prayer_alarms_cleaned_v1 = true` immediately.
  - If some were stopped, NONE failed, but 1 was actively ringing $\implies$ **DEFER WRITING MARKER** to the next session (or app resume). No error is thrown. On the next session, audio has finished, zero legacy alarms are found, and the marker is permanently written.
  - If any alarm failed to stop $\implies$ Marker NOT written; retry next session.
- **Updated Document:** `Phase_2A.1_Legacy_Cleanup_Contract.md` (Section 3).

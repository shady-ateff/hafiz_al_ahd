## 2. Test Harness Correction: Fault Injection Hit Tracking

### 2.1 The Problem Resolved
Under the legacy scheduler, `ScheduleWeeklyPrayersUseCase` uses sequential IDs (`int notificationId = 1; currentId++`). When fault injections were registered against deterministic IDs (e.g. `26110900`), the legacy scheduler never invoked the repository with `id = 26110900`. 

Previously, Tests 21 and 22 appeared to "pass" because the legacy `cancelAllAlarms()` cleared only alarms, leaving pre-seeded notifications untouched. The test asserted that the pre-seeded notification survived, falsely crediting the scheduler with Verify-Before-Cancel protection when in reality the fault never fired!

### 2.2 The Solution Implemented
In `test/features/notifications/scheduler_production_path_integration_test.dart`:
1. **Hit Tracking Counters Added:**
   ```dart
   int l1AlarmScheduleFailureHits = 0;
   int l2AlarmVerificationFailureHits = 0;
   int l1NotificationScheduleFailureHits = 0;
   int l2NotificationVerificationFailureHits = 0;
   int iqamaFailureHits = 0;
   int postPrayerAzkarFailureHits = 0;
   int morningAzkarFailureHits = 0;
   int eveningAzkarFailureHits = 0;
   ```
2. **Explicit Hit Assertions in Tests 21–24:**
   ```dart
   expect(
     fakeRepo.l1AlarmScheduleFailureHits,
     greaterThan(0),
     reason: 'Fault injection was not triggered: Scheduler did not call scheduleAdhanAlarm with expected deterministic ID ($alarmId)',
   );
   ```
3. **Result:** Tests 21, 22, and 24 now fail with clear forensic diagnostic messages, proving that the legacy scheduler fails to trigger the injected faults.

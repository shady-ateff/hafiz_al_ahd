## C. Verified API Findings & Unverified Classifications

### 1. Verified from Source Code & Package Reality:
- **`package:alarm` 5.12.0:**
  - `Alarm.set()` schedules exact alarms via Android's native `AlarmManager.setExactAndAllowWhileIdle()` using `PendingIntent.FLAG_UPDATE_CURRENT`.
  - `Alarm.stop(id)` sends a platform channel call to terminate the native `AndroidAlarmService` foreground service and release the audio player.
  - `Alarm.isRinging(id)` queries native service state to report whether audio is actively playing.
  - `Alarm.getAlarm(id)` queries in-memory / SharedPreferences plugin registry (not low-level Linux/Android kernel queues).
- **`flutter_local_notifications` 21.0.0:**
  - `zonedSchedule()` registers a pending exact alarm via `AlarmManager`.
  - `pendingNotificationRequests()` queries persisted scheduled notification requests.
  - `cancel(id)` dismisses pending intents and status bar notifications for that specific ID.
  - Has zero cross-over or shared lifecycle with `package:alarm`.

### 2. Explicitly Classified as `Unverified` (Cannot Be Proven in Software Alone):
- **OEM Battery Restrictor Interventions:** Whether aggressive OEM battery engines (e.g. Xiaomi MIUI / HyperOS, Huawei EMUI, Samsung OneUI Sleeping Apps) will allow exact alarms to wake the device when deep doze is active cannot be statically proven in Dart code. This requires physical device testing.
- **Kernel-Level Alarm Delivery:** Android OS provides no API to query the low-level Linux kernel alarm timer. Verification is bounded at Level 2 (plugin registry) and Level 3 (OS intent acceptance).

## D. Final Architecture Decisions

1. **Targeted Cancellation Invariant:** `cancelAllAlarms()` and `cancelAllNotifications()` are permanently excluded from scheduling.
2. **Deterministic Calendar ID Formula Frozen:**
   $$\mathbf{ID} = (\text{year} \pmod{100}) \times 1,000,000 + (\text{month} \times 10,000) + (\text{day} \times 100) + (\text{prayerIndex} \times 10) + \text{typeOffset}$$
3. **Temporal Guard Window:** Destructive cancellation is blocked if $|\text{now} - T_{\text{scheduled}}| \le 15\text{s}$ or if `Alarm.isRinging(id) == true`.
4. **Transition Execution Order:** `Schedule New ➡️ Verify Level 1+2 ➡️ Targeted Cancel Old`.
5. **Contiguous Completion Horizon:** `scheduled_until_date` advances strictly to the last unbroken day where all 5 prayers, iqamas, and azkar succeeded.

## F. Remaining Risks

1. **Cross-Process Asynchrony (Platform Channel Boundary):** Because Dart and Android Java/Kotlin run in separate threads and processes, atomic two-phase commit is physically impossible without custom native NDK locks. Mitigation: The $\pm 15$s temporal guard and non-destructive transition order provide industry-standard best-effort protection.
2. **Aggressive OEM Doze Modes:** Devices with non-standard power managers may delay alarms if the user has not granted "Unrestricted Battery" permission. Mitigation: User education and explicit permission request in Settings screen.
3. **Reboot Persistence on Chinese OEMs:** Some Android forks require "Autostart" permission to reschedule alarms after reboot.

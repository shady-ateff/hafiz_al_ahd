## 1. Executive Summary

In **Phase 2C.3.1**, we successfully implemented and thoroughly verified the **Deterministic Calendar Scheduling Identity Contract** (`CalendarAlarmIdContract`).

This contract establishes a mathematically rigorous, collision-free, 32-bit integer identity space for all scheduled prayer alerts and auxiliary notifications over the calendar range **2024 to 2099**.

### Key Deliverables & Achievements
1. **Pure Domain Contract:** Created `lib/features/notifications/domain/entities/calendar_alarm_id_contract.dart` with zero Flutter framework dependencies.
2. **Deterministic Formula:** Encoded date, prayer index, and alert type offset into a structured 8-digit integer:
   $$\text{ID} = (\text{year} \pmod{100}) \times 1,000,000 + \text{month} \times 10,000 + \text{day} \times 100 + \text{prayerIdx} \times 10 + \text{typeOffset}$$
3. **Fail-Closed Boundary Protection:**
   - Rejects UTC `DateTime` (`isUtc == true`) via `ArgumentError` to prevent silent timezone date shifts.
   - Rejects `PrayerAlertDecision.none` via `ArgumentError` (an `off` alert does not generate an ID).
   - Validates ranges for year ($2024..2099$), month ($1..12$), day ($1..31$), prayer index ($0..4$), and type offset ($0..9$).
4. **Collision Isolation:**
   - Strict disjointness between Alarms, Notifications, Iqama, and Azkar.
   - Guaranteed isolation from reserved system IDs ($888, 999, 8888$) and legacy sequential IDs ($1..100$).
5. **Comprehensive Verification:**
   - **23/23 tests PASS** in `calendar_alarm_id_contract_test.dart` (including an exhaustive 7-day 182-event pairwise collision matrix).
   - **Static Analysis:** `0 issues found` (`flutter analyze`).
   - **Full Regression Baseline:** All 10 existing test suites pass with 100% fidelity to previous baseline (including the expected 6 RED tests in Group A awaiting Phase 2C.6).

  - `Fajr = 0`
  - `Dhuhr = 1`
  - `Asr = 2`
  - `Maghrib = 3`

- **Type Offsets ($0..5$ assigned, $6..9$ reserved):**
  - `offsetPrayerAlarm = 0`
  - `offsetPrayerNotification = 1`
  - `offsetIqama = 2`
  - `offsetPostPrayerAzkar = 3`
  - `offsetMorningAzkar = 4` (anchored to Fajr index `0`)
  - `offsetEveningAzkar = 5` (anchored to Asr index `2`)

### 2.3 Identity Space Bounds
- **Minimum Contract ID:** `24010100` (2024-01-01 Fajr Alarm)
- **Maximum Contract ID:** `99123149` (2099-12-31 Isha Reserved Offset 9)
- **Safe 32-bit Integer:** Max value `99,123,149` $\ll 2^{31}-1$ ($2,147,483,647$), fitting comfortably in Android `int` / SQLite 32-bit signed integers.

## 5. Architectural Invariants Enforced

1. **Production Behavioral Freeze:**  
   `ScheduleWeeklyPrayersUseCase` and `SchedulePrayerUseCase` were **NOT modified** in this phase. Existing sequential integer IDs continue running undisturbed in production code until Phase 2C.4.
2. **Domain Purity Invariant:**  
   `CalendarAlarmIdContract` lives in `lib/features/notifications/domain/entities/` and has zero references to Flutter or third-party scheduling packages.
3. **Temporal Invariant:**  
   Intraday time components (hours, minutes, seconds, milliseconds) do not alter the ID. An alert rescheduled to a different minute on the same calendar day retains its deterministic identity.
4. **Timezone Shift Protection:**  
   UTC timestamps are rejected at entry with `ArgumentError`, forcing all callers to provide calendar-local date objects.
